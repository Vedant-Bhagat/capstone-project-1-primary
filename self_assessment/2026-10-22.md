  - **Acted on Janhavi's review, which found a real error in my schema recommendation.** I had claimed that
    indexing the filter column makes MariaDB pre-filter a vector query and return correct results. I tested
    that at 1% selectivity and generalised from it. She tested at ~12%, which is the selectivity our corpus
    actually plans to use, and found the optimizer abandons the pre-filter and silently under-returns.
    Reproduced it myself before changing anything: 0 rows returned on two of three runs where 250 rows match
    the filter.
  - Diagnosed it properly rather than just patching the text. Ruled out `ANALYZE TABLE` as the cause (the
    plan is identical with and without it) and ruled out range predicates (correct at every selectivity from
    1% to 50%), then swept equality selectivity to locate the crossover: safe and exact up to 6.2%,
    post-filtered and unreliable from 8.3% upward, so roughly 7% on this harness.
  - Established the fix: `FORCE INDEX` on the filter column restores the safe plan deterministically and
    gives results identical to exhaustive search — 10 of 10 across four rebuilds, against the default plan
    returning 0 on three of those four.
  - Corrected every document that had stated the original mitigation as proven — `09_verified_findings.md`
    (new finding 7b), `05_schema.md`, `03_corpus.md`, `06_retrieval.md`, `07_evaluation.md` and the README —
    and credited Janhavi in both the spec and the README rather than quietly folding the correction in.
  - The corrected finding is sharper than the original: MariaDB's vector index does not currently serve
    selective filtered queries at all. You either accept approximate results that are sometimes empty, or
    force an exact scan over the filtered subset and the vector index contributes nothing. That is a better
    headline than the one we started with, and it came from a teammate's review.
  - Added two tests to the spec's CI plan as a guard against our own future selves: one asserting every
    committed hybrid query still contains `FORCE INDEX`, and one asserting no category on the real corpus
    exceeds the crossover selectivity.

## Pranesh

- **Work done this week:** Component A (corpus and ingest), all on branch `pranesh/ingest-pipeline`.
  - **First pieces of the ingest** (`bf3429f`): `python/config.py` holding every parameter,
    `python/chunk.py` as a pure function with no I/O (whole sentences up to 300 words, 50-word overlap,
    never across a section heading, 40-word minimum) with 15 unit tests, and a first `python/fetch.py`.
    Checking the API before relying on it showed whole-article extracts come one per request, not in batches
    of 20 as the spec assumed, so I corrected `03_corpus.md`. Inspected the chunker's output on a real
    article (Emperor penguin, 26 chunks) before committing it. Added two rules to `04_chunking_embedding.md`
    that the spec did not have: skip reference/link-list sections, and cut a run-on "sentence" over 300
    words rather than let the model truncate it.
  - **Category survey, which changed the corpus plan** (`3ee0eff`, `fde6503`). Measured the spec's eight
    categories against the live Wikipedia API instead of trusting the estimates. Four were far too thin to
    sample ~150 articles from: Birds 28, Classical composers 22, Human spaceflight 85, Philosophical concepts
    5. Surveyed about 30 candidates for article count, article size (to catch stub-heavy categories that
    look big but produce little text) and overlap between categories, and proposed replacements. The team
    chose nine categories, ~1,295 articles. Wrote that into `03_corpus.md` with the live counts, a
    150-per-category cap taking the longest articles first, and a first-in-config-order-wins overlap rule.
    The spec's first wording of the overlap rule was ambiguous between "member of" and "selected by" an
    earlier category; the team chose membership and the spec now says so explicitly. Then implemented both
    rules in `config.py` and `fetch.py` and checked them against live listings for three categories: 450
    articles selected, no duplicates, all 16 articles shared by `political_philosophy` and `ethics` kept out
    of `ethics`, and the tie-break checked on a synthetic case.
  - **Revision-pinning redesign** (`34ee52a`, `1f1d52a`). While planning the `--manifest` reproduction path
    I found it could not work as specified: the TextExtracts API **silently ignores the requested
    revision**. Asked for a 2023 revision it returns today's text while still reporting the old revid, and
    it has no `oldid` parameter. Investigated what the live API does support before writing any code, and
    the team chose to render each revision with `action=parse&oldid=` and convert the HTML ourselves. Wrote
    `python/htmltotext.py` (standard library only, about 100 lines) and moved `fetch.py` to fetch by pinned
    revid, with the category listing returning each article's revid in the same request. Verified live that
    the same revid fetched twice is byte-identical, that old and current revisions differ as expected, and
    that on the same revision the new converter matches the old extract API sentence for sentence and gives
    identical chunks. 36 unit tests across chunker and converter, against two saved real revisions (Emperor
    penguin, and Active and passive transformation for maths: all 69 formulas kept as LaTeX). Each drop rule
    was mutation-checked, i.e. disabled in turn to confirm a test fails; that check found one rule
    (`noprint`) whose test passed for the wrong reason, which is now fixed.
  - **Manifest design** (`3987130`). Rewrote `03_corpus.md`'s Fetching and Reproducibility sections to
    match the code, stated the one real limitation as accepted rather than leaving it implicit (templates
    such as unit conversions render with today's template code, so a reproduction can rarely differ in
    formatting), and designed `corpus_manifest.csv` with a SHA-256 of each article's text, so a reproduction
    can report how closely it matched instead of assuming it did.
  - **Spec consistency sweep** (`11e21da`). The category change left eight / ~1,200 / ~12,000 figures across
    11 files. Updated them file by file, left past measurements and still-accurate figures alone, and wrote
    the chunk count as "~13,000 (unverified)" rather than inventing a precise number. Recorded the category
    and manifest choices as decided in `12_open_decisions.md` (D4, new D8).
