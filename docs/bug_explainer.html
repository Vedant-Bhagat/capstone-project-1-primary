No error message, no warning, and the program carries on as if the answer were correct. We think this is a genuine defect in MariaDB, and we would like to report it. This page is the case, from scratch.

Asking to send one comment to MariaDB
Golden Record · Vedant, Janhavi, Pranesh 2 November 2026 MariaDB 11.8, 12.3.3, current release

What the project does

Searching text by meaning, inside the database

MariaDB recently learned to search by meaning rather than by keyword. Our project measures how well that works. In the course of measuring it, we found a case where the database quietly gives the wrong answer.

The technique is standard. Each paragraph of text is converted by a language model into a list of numbers, and paragraphs about similar things end up with similar numbers. "Nearest" in that number space means "closest in meaning". We loaded 1,289 Wikipedia articles, cut into 18,651 paragraphs, and asked the database for the paragraphs nearest to a question.

Searching all 18,651 paragraphs one by one is exact but slow, so databases build an index: a shortcut structure that finds the near ones without looking at everything. The shortcut is approximate by design, and trading a little accuracy for speed is expected and fine. Returning nothing at all is not.

The symptom

One query, two ordinary conditions

Our test table has 2,048 rows. Each row carries a category number from 0 to 7, so each category holds exactly 256 rows. The query says: of the rows in category 4, give me the 10 nearest to this point.

SELECT id
FROM   t
WHERE  cat = 4                             -- 256 of the 2,048 rows match this
ORDER BY VEC_DISTANCE_COSINE(v, @query)    -- nearest first
LIMIT  10;                                -- so: the 10 nearest of those 256

There is nothing exotic here. Both conditions are the kind every application writes. The expected answer is 10 rows. The actual answer is an empty result, with SHOW WARNINGS empty and the program's exit status reporting success.

Running it for every category at once shows the shape of the problem. Six of the eight categories return nothing:

The control

The same question, asked three ways

This is the part that makes it a defect rather than a misunderstanding on our side. SQL lets you tell the database which shortcut to use. The data, the question and the answer required are identical in all three cases. Only the route changes.

Database chooses

0 — no hint —

It picks the vector shortcut and returns an empty result.

Filter first

10 FORCE INDEX (ix_cat)

Find the 256 rows in the category, then measure each one. Correct.

No shortcut at all

10 IGNORE INDEX (v)

Measure every row in the table. Correct, and the definition of the right answer.

The rows exist, the database can reach them, and two of the three routes find them. The route it chooses on its own is the one that fails. That is the whole argument.

The mechanism

Why the shortcut comes back empty

The shortcut is a map of which rows are near which other rows. To answer a query it starts near the question and walks outward a limited number of steps, collecting candidates. Only afterwards does it check the category condition and throw away whatever does not match.

This also explains the odd column in the table above. What predicts failure is not how rare the category is, since all eight are equally common here, but how far it sits from the question.

Due diligence

Four explanations we tested and eliminated

Each of these was a plausible way for us to be wrong. We checked all four, and two of them corrected our own earlier claims.

"The category is too rare"

No. All eight categories are exactly 12.5% of the table, and they do not behave alike. Rarity does not explain it.

"Too far is too far"

Also no, and this one cost us a claim. Categories 7 and 1 sit at distance 0.0326 and 0.0332, two per cent apart, and one returns nothing while the other returns everything. Distance ranks the risk. It does not draw a line, and we no longer say it does.

"Search harder"

The documented remedy is to widen the search. We tried 10, 100 and 2,000 steps, the last being the size of the entire table. All three return zero rows.

"Build a denser index"

Helps, unpredictably. Going from the shipped density to the next one up fixes five categories and breaks one that previously worked. One category stays broken at every density we tried. It is a reshuffle, not a fix.

One more detail matters, because it is why this bug has survived. Below roughly 768 rows the database stops choosing the shortcut, filters first, and is perfectly correct. Shrink the test case and the bug disappears.

Prior art

Before writing anything we searched their tracker, which changed what we are sending. We are not claiming to have discovered this. It is reported, accepted, and still present.

It reproduces on machines that are not ours

Our reproduction is 2,048 rows generated by arithmetic inside the database. No downloads, no language model, no random numbers, so it loads identically on anyone's computer, and it runs in about one second. Calibration

How sure we are, claim by claim

These four are not equally certain, and the report rests only on the first two. Separating them is the point. A single number for "it is a bug" would hide where the doubt actually sits.

~99% The behaviour happens Identical across five runs and five rebuilds of the index, and reproduced on GitHub's machines against three server versions. For this to be wrong, a public build log would have to be wrong.
~90% It is a defect, not intended behaviour Mostly because MariaDB already decided this. They accepted the same symptom as a bug and fixed it once, and two more in the family are confirmed open. No warning is raised either, and deliberate truncation would normally warn.
~60% It is the same defect that was fixed in 11.7.1 Same symptom, same query shape, but code paths are not visible from SQL. Incomplete fix, regression, or a separate bug that looks identical are all live. This is why the comment asks rather than asserts.
~50% MariaDB acts on it Independent of whether we are right. Four tickets in this family are already open, or closed without resolution.

The one way we are meaningfully wrong: a maintainer replies that the vector index was never meant to serve a query with an unrelated WHERE, that FORCE INDEX is the intended pattern, and closes it as a known limitation. We put that at roughly one in ten, and our own code comments already concede that this index does not currently serve selective filtered queries. What argues against it is that they fixed the earlier ticket instead of saying exactly that.

The record

We have published the wrong thing about this twice

Both retractions are in the repository, each with the measurement that forced it. A finding that has been corrected twice should be presented by the people who corrected it, and in those words.

Withdrawn 22 October "It does not reproduce on real embeddings."

We had run it against the real corpus, seen it behave correctly, and recorded that as a limit on the finding. The test was faulty. The filters we happened to pick pointed in the same direction as the question, which is the one arrangement in which the shortcut cannot fail.

It does reproduce on real embeddings. The limit was a false negative of our own making, and it sat in the repository for six days.
Withdrawn 28 October "The failure is deterministic."

Replaced when five rebuilds of the same index over the same rows answered the same query with 10, 0, 2, 3 and 0 rows.

On the real corpus it moves between runs and we cannot explain why. The small reproduction is stable, so it is evidence for the shortfall and not for the instability, and we say so in the report.

Neither correction touched whether the under-return happens. Both were about how we described it. That distinction is the reason we are willing to send anything at all.

The limits

What we are deliberately not claiming

We have been wrong about this finding twice already, in public, in our own repository. Both retractions are recorded there with the measurement that forced them. These four lines go into the report itself rather than being left for a reviewer to find.

  1. We do not know whether this is the same underlying flaw as the one fixed in 11.7.1. It could be an incomplete fix or a separate problem with the same symptom. We offer to open a separate ticket if they say so.
  2. On the real 18,651-paragraph corpus the failure moves between identical runs. We cannot explain that. A MariaDB developer has posted a plausible theory on a stalled ticket of his own; verifying it needs a special build of the server, not a query, so we cite nobody's theory as our cause.
  3. MariaDB's documentation does describe rows being silently dropped in a related situation. It is a different situation from ours, but close enough that a reviewer might reasonably point at it, which is why our report shows the query plans and the measurements rather than simply asserting a bug.
  4. Our second finding is not a bug and is not in this report. The shipped index density reaches 83% accuracy on our corpus where a denser one reaches 99%. That is a default we think is set too low, which is an opinion, so it goes separately and last. Two similar reports from other people were declined.

The contribution

What the comment adds, and what it does not

The difference between these two columns is the difference between a useful report and a nuisance, so it is worth stating before sending rather than after.

What it adds

  • A test case that runs. The ticket was closed for want of exactly this and the request is still unanswered. One second, nothing to download.
  • Why shrinking it fails. Below about 768 rows the database stops choosing the shortcut and the symptom vanishes. That is probably why the original reporter could not reduce their 250 MB case, and it appears nowhere in the tracker.
  • A version to prioritise by. The newest release is the worst of the three, against a fix recorded two versions ago.
  • Two dead ends closed. Widening the search recovers nothing, and a denser index repairs five categories while breaking one. Neither suggestion needs to be made.

What it does not add

  • A cause. No code pointer and no patch. Every part of the real diagnosis stays with them.
  • A new symptom. They know the symptom; it is in four tickets. We supply the missing evidence, not the observation.
  • Anything on the instability. Deliberately. The one plausible theory needs a build of the server we do not have.
  • Any claim on their time. If the answer is "known limitation", that is a complete answer and we will have cost them two minutes.

So: a good bug report, not a discovery. The realistic best outcome is that a maintainer reproduces in one second something they currently cannot reproduce at all.
